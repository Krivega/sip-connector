# VideoSendingBalancer

Класс для управления балансировкой видео-потоков в SIP-соединении: выставляет отправителю видео
`scaleResolutionDownBy` и `maxBitrate` по команде сервера, размеру трека и клиентскому потолку
(`getMaxResolution`).

## Правила модуля

- Команда сервера применяется только в состоянии `started` и только подключённому (`attach`)
  отправителю.
- Если команда принята в `started` или произошёл `start()`, пока идёт замена трека, параметры нового
  трека применяются сразу, не дожидаясь конца замены.
- Пока запуск запланирован (`warmup`), балансировщик параметры не ужесточает: только ослабляет.
  Браузер в это время прогревает отправку, и скалирование применять нельзя.
- Сброс в `idle` возвращает параметры по треку и клиентскому потолку (`getMaxResolution`). Сам
  клиентский потолок во время прогрева выставляет `SipConnector` через `sendEncodings`.
- Операция прошлого запуска или звонка не применяет состояние нового.
- Замены трека одного отправителя идут в порядке вызова, ни одна не теряется.
- Балансировщик пишет параметры только по своим поводам: команда, старт, сброс, замена трека,
  изменение собственных входов (отправитель, его трек, размер трека), повтор после своей ошибки.
  Чужие изменения параметров отправителя он не перезаписывает.

### Состояния

Состоянием владеет `VideoSendingBalancer`. Каждый переход создаёт новый объект состояния; его
идентичность отличает операции прошлого состояния и служит токеном запуска (`runToken`).

| Переход    | Что делает                                                                                |
| ---------- | ----------------------------------------------------------------------------------------- |
| `warmUp()` | `warmup`: включает перехват `replaceTrack`, параметры не трогает. Из `started` — ничего   |
| `start()`  | `started`: дополняет подготовку идущей замены, включает сверку, затем первая балансировка |
| `stop()`   | `idle`: останавливает сверку, стирает команду, отключает перехват, ставит сброс в очередь |

### Что применяется

Решает состояние на момент выполнения операции, а не её постановки.

| Операция                | `idle`         | `warmup`                 | `started`                                         |
| ----------------------- | -------------- | ------------------------ | ------------------------------------------------- |
| Команда сервера         | не принимается | только запоминается      | подготовка идущей замены, балансировка с командой |
| Сверка по тику          | не идёт        | не идёт                  | балансировка с командой, если входы изменились    |
| Ручной `balance()`      | по треку       | ничего                   | с командой                                        |
| Сброс от `stop()`       | по треку       | то же, только ослабление | подключённому — с командой, чужому — по треку     |
| Подготовка замены       | не выполняется | не выполняется           | строжайшее из текущего и нового трека, с командой |
| Применение после замены | не выполняется | не выполняется           | фактический трек, с командой                      |
| Откат неудачной замены  | по треку       | то же, только ослабление | подключённому — с командой, чужому — по треку     |

- «По треку» — по разрешению трека и клиентскому потолку, без команды сервера.
- «С командой» — состояние `started` и отправитель подключён. Условие определено один раз в
  `VideoSendingBalancer`, `TrackReplacer` получает его предикатом. Отправителю прошлого звонка
  команда нового чужая.
- «Только ослабление» — масштаб не больше текущего; битрейт не меньше текущего, а если у отправителя
  нет потолка битрейта или кодек неизвестен, битрейт не трогается.
- Отправитель без трека получает масштаб 1 и максимальный битрейт кодека в любом состоянии, в том
  числе после `replaceTrack(null)` в `started`: трек, который на нём появится, не должен унаследовать
  прежнее ограничение.
- Обычная балансировка сверяет идентичность состояния в задаче очереди: начатая в прошлом состоянии
  параметры не применяет и завершается с `isChanged: false`. Сброс и откат идентичность не сверяют —
  что им применить, определяет таблица.
- Команда `MAX_MAIN_CAM_RESOLUTION` с некорректным разрешением (не два положительных числа
  «ШИРИНАxВЫСОТА») не принимается: в силе остаётся прежняя команда. Разрешение проверяется только при
  приёме команды; расчёт получает уже проверенное.
- Исключение подписчика `onSetParameters` логируется и операцию не отклоняет.

### Кодек

Кодек запрашивает только обычная балансировка (`getStats`), до очереди: зависший запрос не
задерживает очередь и замену трека. Сброс, подготовка замены, применение после замены и откат берут
кодек, полученный последней балансировкой этого отправителя. Если в статистике кодека нет (например,
отправка ещё не согласована), остаётся последний известный кодек отправителя. Пока кодек неизвестен,
меняется только масштаб, а при заданном `ignoreForCodec` параметры не меняются; не меняются они и для
исключённого кодека. Балансировку без кодека сверка по тику повторяет, пока кодек не станет известен.

### Замена трека

С начала прогрева `TrackReplacer` перехватывает `replaceTrack` отправителя. Каждая замена — одна
задача очереди отправителя:

1. Подготовка — цепочка звеньев: строжайшие параметры из рассчитанных для текущего и нового трека.
   Первое звено добавляет сама задача, следующие — команда, принятая в `started`, и `start()`, пока
   замена идёт. Звенья выполняются друг за другом; ошибка звена логируется и замену не отменяет.
2. Оригинальный `replaceTrack` вызывается, когда цепочка перестала расти; после его возврата задача
   снова дожидается цепочки.
3. При его ошибке — откат подготовки этой замены, если выполнялось хотя бы одно звено; замена
   отклоняется этой ошибкой.
4. После успеха, в той же задаче — параметры трека, оказавшегося на отправителе. Затем, уже после
   задачи, обычная балансировка: она получает свежий кодек и перекрывает параметры, которые
   вызывающий код выставляет сразу после `replaceTrack`.

Подготовка и применение после замены выполняются только в `started` и только подключённому
отправителю; иначе перехват лишь ставит замену в очередь — порядок сохраняется, параметры не
меняются. Перехват остаётся на отправителе, пока не завершены принятые им замены, и на отправителе
без трека, пока тот есть в соединении и в нём нет другого видео-отправителя с треком.

### Сверка по тику

Весь `started` тикер (`TrackMonitor`) сравнивает отправителя, его трек и размер трека с теми, по
которым параметры применены в последний раз. Совпало — ничего не делает: не запрашивает кодек и не
читает параметры отправителя. Не совпало, либо последняя балансировка завершилась ошибкой или прошла
без кодека, либо при
замене трека у подключённого отправителя не встали параметры подготовки, применения после замены или
отката — обычная балансировка. Так замечаются замена трека мимо перехвата, смена отправителя, изменение размера и
собственные сбои.

Следующий тик планируется после завершения балансировки предыдущего. Интервал удваивается до
`16 × pollIntervalMs`, пока параметры не меняются, и возвращается к начальному, когда балансировка
их изменила, завершилась замена трека или при замене не встали параметры. Пока в соединении нет
видео-отправителя с треком, интервал не растёт: появившегося отправителя ограничит ближайший тик.

### Очередь

В `TaskQueue` у каждого отправителя своя очередь изменений: применение параметров и замена трека
выполняются строго в порядке постановки. Команда сервера и трек читаются в момент выполнения
задачи. `stop()`, `warmUp()` и `start()` очередь не сбрасывают. Сброс ставится в очередь прямо в
`stop()` — после замен, принятых до остановки.

## Известные пределы

- Таймаутов для операций браузера нет. Зависший `setParameters` или `replaceTrack` держит очередь
  своего отправителя насовсем (у следующего звонка свой отправитель и своя очередь). Зависший
  `getStats` не завершает свою балансировку; если она начата сверкой по тику, сверка замирает до
  следующего запуска или замены трека.
- Кодек берётся из последней балансировки и может быть неизвестен или устареть. При заданном
  `ignoreForCodec` и неизвестном кодеке подготовка замены и сброс параметры не меняют.
- Сбой подготовки замену не отклоняет: трек заменяется с прежними параметрами, новые применяются
  после замены.
- Команда или `start()` во время уже идущего оригинального `replaceTrack` применяются сразу, но
  параллельно с ним: успеют ли параметры к первому кадру нового трека, решает браузер.
- Расхождение, которое замечает только сверка по тику, исправляется в пределах её интервала.
- Вызывающий код может записать свои параметры сразу после `replaceTrack` (`sendEncodings`): до
  балансировки после замены действуют они.
- Команда сервера стирается при `stop()`: следующий запуск начинает без неё.
- Камера и презентация различаются только наличием трека у отправителя камеры.
- Чужие изменения параметров отправителя не перезаписываются, пока не изменились входы
  балансировщика; смена одного клиентского потолка без других поводов тоже не замечается.
- Замена, вызванная после возврата оригинального `replaceTrack`, идёт мимо очереди.

## Использование

```typescript
import VideoSendingBalancer from './VideoSendingBalancer';

const balancer = new VideoSendingBalancer(getConnection, {
  ignoreForCodec: 'H264',
  getMaxResolution: () => connectionConfiguration?.maxAvailableResolution,
  onSetParameters: (parameters) => {
    console.log('Параметры обновлены:', parameters);
  },
  pollIntervalMs: 1000,
});

balancer.warmUp(); // запуск запланирован
balancer.handleServerHeaders(headers); // команда сервера
await balancer.start();
await balancer.balance(); // ручная балансировка
balancer.stop();
```

Балансировщик не подписывается на события звонка и `main-cam-control`: их слушает
`VideoSendingBalancerManager` и вызывает переходы.

## API

```typescript
constructor(
  getConnection: () => RTCPeerConnection | undefined,
  options: IBalancerOptions & {
    pollIntervalMs?: number;
  },
)
```

```typescript
interface IBalancerOptions {
  ignoreForCodec?: string;
  onSetParameters?: TOnSetParameters;
  getMaxResolution: () => TResolutionSize | undefined;
  isExcludedSender?: (sender: RTCRtpSender) => boolean;
}
```

`getMaxResolution` вызывается при каждом расчёте параметров. Потолок не применяется при
`PAUSE_MAIN_CAM` (фиксированный `scaleResolutionDownBy: 200`) и при `MAX_MAIN_CAM_RESOLUTION` с
разрешением — там действует только команда.

`isExcludedSender` — отправители, которых балансировщик не выбирает: не балансирует, не подключает
перехват замены трека, не сбрасывает и не сверяет по тику. Если других видео-отправителей с треком
нет, балансировщик ничего не записывает. `SipConnector` исключает так отправителя идущей демонстрации
(`PresentationManager.isPresentationSender()`): без камеры первым видео-отправителем с треком
оказалась бы демонстрация. После остановки демонстрации тот же отправитель (например, с камерой)
снова балансируется.

- `warmUp()`: начать прогрев
- `start()`: запустить балансировку; возвращает результат первой балансировки
- `stop()`: остановить балансировку и сбросить параметры отправителя
- `handleServerHeaders(headers)`: принять команду управления главной камерой
- `balance()`: выполнить балансировку; отклоняется ошибкой запроса кодека или применения параметров
- `runToken`: токен действующего запуска

## Компоненты

- `SenderBalancer`: расчёт и применение параметров к отправителю, без состояния
- `resolveEncodingParameters`: чистые функции расчёта параметров
- `TrackReplacer`: перехват `replaceTrack` и последовательность замены трека
- `TrackMonitor`: тикер сверки с адаптивным интервалом
- `TaskQueue`: строго последовательные очереди операций, своя у каждого отправителя
- `CodecProvider`: кодек отправителя из `getStats` и последний полученный кодек

## Команды сервера

- `PAUSE_MAIN_CAM`: понижение разрешения до минимума
- `RESUME_MAIN_CAM`: параметры по разрешению трека с учётом `getMaxResolution`
- `MAX_MAIN_CAM_RESOLUTION`: ограничение по `resolutionMainCam`; без разрешения — как
  `RESUME_MAIN_CAM`
- `ADMIN_STOP_MAIN_CAM` / `ADMIN_START_MAIN_CAM`: параметры по разрешению трека
