# VideoSendingBalancer

Класс для управления балансировкой видео-потоков в SIP-соединении.

## Архитектура

Класс полностью инкапсулирует всю логику балансировки видео, включая:

- Поиск видео-sender в соединении
- Запрос кодека отправителя до очереди и исключение по кодеку (`ignoreForCodec`)
- Применение команды управления камерой, переданной `VideoSendingBalancerManager`
- Управление состоянием балансировки
- Расчёт параметров кодирования по команде сервера (`resolveEncodingParameters`)
- Единую очередь изменений отправителя: применение параметров и замена трека

## Использование

### Создание экземпляра

```typescript
import VideoSendingBalancer from './VideoSendingBalancer';

const balancer = new VideoSendingBalancer(getConnection, {
  ignoreForCodec: 'H264',
  getMaxResolution: () => connectionConfiguration?.maxAvailableResolution,
  onSetParameters: (parameters) => {
    console.log('Параметры обновлены:', parameters);
  },
  pollIntervalMs: 1000,
});
```

`getMaxResolution` — обязательная опция `IBalancerOptions`. Callback передаётся в `SenderBalancer`
при создании и вызывается при каждой балансировке и сбросе, чтобы учесть актуальное значение
`maxAvailableResolution` из конфигурации подключения.

В типичном сценарии `getMaxResolution` задаёт `SipConnector` при создании
`VideoSendingBalancerManager`.

### Команда сервера

```typescript
balancer.setServerHeaders(headers);
await balancer.balance();
```

Балансировщик не подписывается на `main-cam-control`: события звонка и команды сервера слушает
`VideoSendingBalancerManager` и решает, когда балансировать. `setServerHeaders()` только сохраняет
команду: в расчёте она участвует после `start()`, применяет её следующая балансировка.

### Запуск

```typescript
await balancer.start();
```

`start()` сразу, до первой балансировки, включает перехват `replaceTrack` и слежение за размером
трека найденного отправителя, затем выполняет балансировку с сохранённой командой.

### Балансировка

```typescript
const result = await balancer.balance();
console.log('Результат балансировки:', result);
```

`balance()` запрашивает кодек отправителя, затем ставит применение параметров в очередь и возвращает
его результат; ошибка запроса кодека или применения параметров отклоняет промис. Таймаута на запрос
кодека нет: при зависшем `getStats` эта балансировка не завершится, но очередь и замена трека от
него не зависят. До `start()` и после `stop()` параметры применяются один раз по разрешению трека:
команда сервера не учитывается, перехват `replaceTrack` и слежение не включаются.

### Остановка

```typescript
balancer.stop();
```

`stop()` стирает команду сервера, сразу возвращает отправителю оригинальный `replaceTrack` и
останавливает слежение, затем выполняет балансировку без команды — она восстанавливает параметры
отправителя по разрешению трека.

## API

### Конструктор

```typescript
constructor(
  getConnection: () => RTCPeerConnection | undefined,
  options: IBalancerOptions & {
    pollIntervalMs?: number;
  },
)
```

```typescript
interface IBalancerOptions {
  ignoreForCodec?: string;
  onSetParameters?: TOnSetParameters;
  getMaxResolution: () => TResolutionSize | undefined;
}
```

### Публичные методы

- `setServerHeaders(headers)`: Сохранить команду управления главной камерой
- `start()`: Включить перехват замены трека и слежение за треком, выполнить первую балансировку
- `balance()`: Выполнить балансировку
- `stop()`: Стереть команду, снять перехват и слежение, восстановить параметры Sender

## Внутренняя логика

Класс использует следующие компоненты:

- `SenderBalancer`: Применение параметров к отправителю по переданному кодеку, команде и треку (без
  состояния); без кодека меняет только масштаб
- `resolveEncodingParameters`: Чистые функции расчёта параметров и выбора более строгих из двух
- `TrackReplacer`: Перехват `replaceTrack` и последовательность замены трека
- `TrackMonitor`: Адаптивный опрос размера трека
- `TaskQueue`: Строго последовательная очередь операций с отправителем
- `SenderFinder`: Поиск видео-сендера в соединении
- `CodecProvider`: Получение кодека из сендера (`getStats`) — только для балансировки, до очереди

## Ограничение разрешения

`SenderBalancer` вызывает `getMaxResolution()` при каждой операции с отправителем:

- `balance()`
- сбросе параметров при `stop()`
- применении параметров до и после замены видеотрека

Лимит влияет на `scaleResolutionDownBy` и `maxBitrate` в `resolveEncodingParameters`.

Исключения:

- `PAUSE_MAIN_CAM` — фиксированное понижение (`scaleResolutionDownBy: 200`), лимит подключения не
  применяется
- `MAX_MAIN_CAM_RESOLUTION` с `resolutionMainCam` — используется только разрешение из команды MCU

## Замена видеотрека

После `start()` `TrackReplacer` перехватывает `replaceTrack` отправителя. Каждая замена — одна
задача общей очереди: она ждёт поставленные раньше изменения отправителя и не пересекается с ними.
Кодек замена не запрашивает.

1. Перед заменой на непустой трек, отличный от текущего, применяется более строгий (больший)
   `scaleResolutionDownBy` из рассчитанных для текущего и нового трека, чтобы кадры нового трека не
   ушли в полном разрешении; ослабления до замены нет, битрейт не меняется. Если задано исключение
   по кодеку (`ignoreForCodec`), параметры заранее не меняются: ограничение ставит балансировка
   после замены. Если применить масштаб не удалось, ошибка логируется, трек всё равно заменяется.
2. Вызывается оригинальный `replaceTrack`.
3. Замена отклоняется только ошибкой самого `replaceTrack`; при этом масштаб трека, оставшегося на
   отправителе, возвращается.
4. После успешной замены слежение за размером перезапускается на новом треке и, если трек не
   пустой, выполняется обычная балансировка; параметры, которые вызывающий код выставляет сразу
   после `replaceTrack`, она затем перекрывает. После замены на пустой трек балансировка не
   запрашивается, перехват остаётся до следующей балансировки: команда сервера или ручной
   `balance()` при пустом треке его снимут. При замене с пустого трека масштаб заранее не ставится,
   ограничение применяет балансировка после неё.

Если во время замены вызван `stop()`, замена дорабатывает до конца; слежение не возобновляется.
После `stop()` вызовы `replaceTrack` идут напрямую, мимо очереди.

## Очередь операций

Через одну `TaskQueue` строго по очереди, в порядке постановки, выполняются только изменения
отправителя: применение параметров и замена трека. Кодек балансировка запрашивает до очереди,
поэтому зависший `getStats` не задерживает очередь и замену трека. `add()` возвращает результат
своей задачи или отклоняется её ошибкой; ошибка одной задачи не останавливает следующие. Команда
сервера и трек читаются в момент выполнения задачи, поэтому поставленная раньше задача применяет
актуальное состояние.

Очередь начинается заново при остановке балансировки: зависший `setParameters` или `replaceTrack`
задерживает следующие операции только до остановки. Таймаутов нет.

## Состояния камеры

- `PAUSE_MAIN_CAM`: Понижение разрешения до минимума
- `RESUME_MAIN_CAM`: Восстановление параметров по разрешению трека с учётом `getMaxResolution`
- `MAX_MAIN_CAM_RESOLUTION`: Установка разрешения по `resolutionMainCam` от сервера
- `ADMIN_STOP_MAIN_CAM` / `ADMIN_START_MAIN_CAM`: Административные команды
