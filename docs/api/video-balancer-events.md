# События `VideoSendingBalancerManager`

`VideoSendingBalancerManager` генерирует события в процессе автоматической балансировки видеопотоков. Все события доступны через префикс `video-balancer:*` в `SipConnector`.

## События

| Имя события                          | Описание                                     | Тип данных              |
| ------------------------------------ | -------------------------------------------- | ----------------------- |
| `video-balancer:balancing-scheduled` | Генерируется при планировании балансировки   | `{ delay: number }`     |
| `video-balancer:balancing-started`   | Генерируется при запуске балансировки        | `{ delay: number }`     |
| `video-balancer:balancing-stopped`   | Генерируется при остановке балансировки      | `Record<string, never>` |
| `video-balancer:parameters-updated`  | Генерируется при обновлении параметров видео | `RTCRtpSendParameters`  |

Поле `delay` в `balancing-scheduled` и `balancing-started` — настроенная задержка запуска
(`balancingStartDelay`), а не фактически прошедшее время. Команда сервера, пришедшая после
`balancing-scheduled`, не ускоряет запуск: `balancing-started` приходит по таймеру или при ручном
`startBalancing()`. Ручной `balance()` во время прогрева запуск тоже не ускоряет: он применяет
параметры по треку без команды, `balancing-started` не генерирует, а изменённые параметры сообщает
событием `parameters-updated`.

`balancing-started` генерируется после первой балансировки, каким бы ни был её исход: запуск
включает режим, а неудавшуюся первую балансировку повторит сверка по тику; `startBalancing()` при
этом не отклоняется, ошибка пишется в лог. Без соединения `startBalancing()` отклоняется ошибкой
`connection is not exist`, балансировка не запускается, и событие не генерируется. Если балансировку
остановили во время первой балансировки, событие не генерируется; если её за это время остановили и
запустили заново, событие генерирует только новый запуск. После `balancing-stopped` событие
`balancing-started` остановленного запуска не приходит. Запрос кодека первой балансировки ждётся не
дольше ~1 с: без ответа она применяет параметры по последнему известному кодеку, и событие приходит.
Первая балансировка, а с ней и событие, ждёт незавершённую замену трека на том же отправителе.

`balancing-scheduled` генерируется и тогда, когда запуск планируется при уже активной балансировке
(`recv-session-ended` без `recv-session-started`): балансировка продолжает работать, повторного
`balancing-started` не будет.

Исключение обработчика `parameters-updated` логируется и не прерывает балансировку.
